# OpenHanako → Jarvis 差距分析

> 目标定位：「真正能帮你完成所有事情的 Jarvis」— 一个全能型个人 AI 助理，在本地运行，有记忆、有灵魂、能主动帮你做事。

---

## 一、现状盘点：你已经有了什么

项目底子非常好，不是从零开始。以下按能力维度汇总当前水平：

| 任务管理 | todo_write / check_pending_tasks / stop_task / wait | 计划跟踪和异步任务管理 |
| 定时 | cron | at / every / cron expression 三种调度模式 |
| 通知 | notify | 桌面和 Bridge 平台通知 |

### 1.2 记忆系统

7 层多级记忆，模拟人类遗忘曲线：

```
原始对话 (JSONL)
  → 滚动摘要 (每 10 轮 / Session 结束)
  → 当日编译 (today.md)
  → 周编译 (week.md)
  → 长期折叠 (longterm.md)
  → 深度记忆 (facts.db, FTS5 + 标签)
  → 置顶记忆 (pinned.md, 永不过期)
```

- 标签匹配 + FTS5 全文搜索 + LIKE 降级三层检索
- CJK n-gram 支持中日韩搜索
- 高斯衰减算法、PII 脱敏
- **自评："目前确实有待优化"**

## 二、差距分析

按重要性分为五个层级：

---

### 层级一：核心可靠性（地基问题）

这些是**当下就影响日常使用体验**的问题，不是锦上添花，是雪中送炭。

#### 2.1.1 记忆系统需要优化

| 项 | 详情 |
|---|------|
| 现状 | README 自述"目前确实有待优化" |
| 影响 | 记忆是 Jarvis 的「灵魂」，记不住/记不准 = 没有连续性 = 没有「认识你」的感觉 |
| 具体表现 | 编译流水线各步骤的 LLM 调用可能因模型不稳定导致空洞；facts.db 规模增大后 FTS5 检索精度下降；当前无向量语义搜索作为补充 |
| 优先级 | **P0** |

#### 2.1.2 Windows 安装包未代码签名

| 项 | 详情 |
|---|------|
| 现状 | `The installer is not yet code-signed` |
| 影响 | SmartScreen 拦截 + "未知发布者"警告，严重影响普通用户的信任和分发 |
| 行业痛感 | EV 代码签名证书约 $300-500/年，但这笔投入对分发 Windows 桌面应用是必需品 |
| 优先级 | **P0** |

#### 2.1.3 电脑控制不稳定

| 项 | 详情 |
|---|------|
| 现状 | "实验性""尝鲜功能""某些软件下可能不稳定" |
| 影响 | 帮你操作桌面软件是 Jarvis 的核心场景之一。不稳定 = 不能依赖 = 每次用都要祈祷 |
| 具体问题 | macOS Accessibility API 对不同应用的兼容性不一致；Windows UIA 树在不同应用中差异大；缺乏统一的错误恢复和等待机制 |
| 优先级 | **P0** |

#### 2.1.4 无 Agent 备份功能

| 项 | 详情 |
|---|------|
| 现状 | README："后续还会添加备份功能" |
| 影响 | 用户花了大量时间调教出来的 Agent 人格、积累的记忆和技能，如果系统重装或目录损坏就全部丢失 |
| 优先级 | **P0** |

#### 2.1.5 空 catch 块（约 172 处）

| 项 | 详情 |
|---|------|
| 现状 | 代码审查发现：abort 调用、首次运行配置、数据库迁移、心跳错误、沙箱进程 kill、上传清理等错误被静默吞掉 |
| 严重位置 | `server/routes/chat.js:769` / `core/first-run.js:113` / `core/migrations.js:281,824` / `lib/desk/heartbeat.js` / `lib/sandbox/exec-helper.js:154,160` / `lib/sandbox/win32-exec.js` / `core/engine.js:1164` / `server/routes/upload.js:172-174` |
| 影响 | 生产环境调试困难，问题被掩盖，用户以为操作成功但实际失败 |
| 优先级 | **P0** |

#### 2.1.6 路由错误未记录服务端日志

| 项 | 详情 |
|---|------|
| 现状 | 几乎所有路由 handler（`sessions.js`, `agents.js`, `config.js`, `desk.js`, `skills.js`）的 catch 块都只返回 JSON 错误给客户端，不做服务端日志记录 |
| 影响 | 生产环境 500 错误无法通过服务器日志追溯，调试全靠猜 |
| 建议 | 在全局 `app.onError` 或每个路由 catch 中统一添加 `log.error` |
| 优先级 | **P0** |

#### 2.1.7 非原子写入（25+ 处）

| 项 | 详情 |
|---|------|
| 现状 | 项目中大量使用 `fsp.writeFile` / `writeFileSync` 直接写入，而非 `tmp+rename` 原子模式。进程崩溃时可能导致文件损坏 |
| 范围 | 约 25+ 处分布在 `core/` 和 `server/` 目录；`core/session-coordinator.js:2245` 的 `session-meta.json` 直接覆写无保护 |
| 影响 | 桌面单进程场景下风险较低，但数据损坏一旦发生就是不可逆的 |
| 修复建议 | 封装 `writeFileAtomic(path, data)` 工具：写入临时文件 → `fs.rename()` 原子替换。优先处理会话元数据、配置文件的写入路径 |
| 优先级 | **P0** |

#### 2.1.8 TOCTOU 竞态条件

| 项 | 详情 |
|---|------|
| 现状 | `server/routes/desk.js:706-707`（`existsSync` + `mkdirSync`）、`desk.js:716-718`（`existsSync` + `renameSync`）、`desk.js:483-491`（技能安装）、`server/routes/sessions.js:931-939`（会话恢复）存在检查-使用竞态 |
| 影响 | 桌面单用户场景下风险低；如未来支持多客户端并发访问，可能出现目录重复创建、文件覆盖冲突 |
| 修复建议 | 改用 `fs.promises` + `try/catch` 模式：直接执行操作，在 catch 中处理 `EEXIST` / `ENOENT`，消除检查与操作之间的时间窗口 |
| 优先级 | **P0** |

#### 2.1.9 移动端仅 v0

| 项 | 详情 |
|---|------|
| 现状 | PWA 初版，能看会话和工作台，但功能有限 |
| 影响 | 手机上是「查看」而非「使用」的定位。真正的 Jarvis 应该能随时随地交互 |
| 优先级 | **P1** |

### 层级二：主动性与上下文理解（从「工具」到「助手」的鸿沟）

当前架构的核心模式是 **「用户问 → Agent 答」**，而真正 Jarvis 应该是：

> **Agent 感知到需要做什么 → 主动做 → 告诉你结果（或在你提问前就已经准备好了答案）**

#### 2.2.1 缺少持续上下文感知

| 项 | 详情 |
|---|------|
| 现状 | Heartbeat 能巡检文件变化，但没有更深层的感知 |
| 缺失 | 用户正在用什么软件？正在参加什么会议？日历上有什么？收件箱有什么？浏览器正在看什么页面？ |
| 为什么重要 | 没有上下文感知，Agent 永远只能被动响应，永远无法在正确的时机说「我帮你处理好了」 |

#### 2.2.2 缺少意图预测

| 项 | 详情 |
|---|------|
| 现状 | Agent 完全被动，用户不说就不动 |
| 缺失 | 看到你打开 IDE → 自动加载项目上下文；看到新邮件 → 自动草拟回复；日历上 15 分钟后有会议 → 提前准备会议材料 |
| 为什么重要 | 这就是「助理」和「工具」的本质区别 |

#### 2.2.3 缺少多步自主规划

| 项 | 详情 |
|---|------|
| 现状 | Agent 能执行单次任务，但不能端到端完成一个复杂目标 |
| 缺失 | 「收到一封邮件 → 理解内容 → 查日历确认时间 → 自动回复 → 创建待办事项 → 通知我」这种完整链路 |
| 为什么重要 | 真正的"帮我完成事情"意味着我可以说一个目标，而不是每一步操作 |
| 技术挑战 | 需要目标分解引擎、进度跟踪、失败重规划、结果验证 |

#### 2.2.4 缺少后台持续运行与主动介入

| 项 | 详情 |
|---|------|
| 现状 | Cron 能做定时触发，Heartbeat 能巡检文件，但它们是被动的定时检查 |
| 缺失 | Agent 在后台持续观察，看到触发条件时立即动作——不是「每 N 分钟检查一次」，而是事件驱动 |
| 为什么重要 | 延迟意味着错过时机。10 分钟巡检一次意味着平均 5 分钟的响应延迟 |

#### 2.2.5 子 Agent 调度弱

| 项 | 详情 |
|---|------|
| 现状 | `ask_agent` 是 fire-and-forget，15 分钟超时，无结果编排 |
| 缺失 | 一个主 Agent 拆解复杂任务 → 分派给多个子 Agent 并行执行 → 汇总结果 → 验证完整性 → 返回用户 |
| 为什么重要 | 复杂任务天然需要并行，当前的单 Agent 模式是瓶颈 |

### 层级三：生态集成（能力边界）

真正帮你「完成所有事情」意味着要接入你实际工作的各种服务。

#### 2.3.1 日历

| 项 | 详情 |
|---|------|
| 缺失 | 无法读取/创建日历事件、无法基于日程主动准备、无法判断用户的空闲/忙碌状态 |
| 理想状态 | 知道你今天有什么安排 → 提前准备材料 → 提醒你 → 会后自动整理纪要 |

#### 2.3.2 邮件

| 项 | 详情 |
|---|------|
| 缺失 | 无法收发邮件、无法摘要收件箱、无法草拟/归档、无法标记重要邮件 |
| 理想状态 | 早上给你一份收件箱摘要 → 对每封重要邮件建议回复 → 你同意后自动发送 |

#### 2.3.3 项目与任务管理

| 项 | 详情 |
|---|------|
| 缺失 | 无法连接 Linear / Jira / Notion / GitHub Issues / Trello |
| 理想状态 | 看到你在某个项目上工作了 2 小时 → 自动更新对应 issue 的进度 → 帮你创建下一个待办 |

#### 2.3.4 知识库 / RAG

| 项 | 详情 |
|---|------|
| 缺失 | 没有文档摄入能力——不能吃你的 PDF、Notion 文档、Confluence 页面然后回答你的问题 |
| 理想状态 | 拖一个 PDF 进来 → Agent 理解内容 → 以后关于这份文档的内容可以直接问答 |

#### 2.3.5 通讯协作

| 项 | 详情 |
|---|------|
| 现状 | Bridge 能做聊天机器人，接收消息并回复 |
| 缺失 | 不能作为你的「分身」主动发起对话、不能在群聊中代表你发言、不能根据上下文判断哪些消息需要提醒你 |

#### 2.3.6 MCP 支持（升级中）

| 项 | 详情 |
|---|------|
| 现状 | MCP Bridge 插件提供间接支持；已有工业级升级计划（`docs/superpowers/plans/2026-05-22-mcp-industrial-upgrade.md`），涵盖 Token 自动刷新、请求重试与指数退避、指标收集、并发请求限制 |
| 已完成 | Token 自动刷新机制（`a88b7f28`）、代码审查修复（`be77dc26`） |
| 待完成 | 请求重试与指数退避、指标收集与结构化日志、并发请求限制、测试覆盖率提升至 >80% |
| 为什么重要 | MCP 社区的几百个 server（数据库、API、文件系统、SaaS）是一个巨大的能力杠杆。原生支持 = 零摩擦接入整个生态 |
| 与向量数据库的对比 | 向量数据库解决「更好地检索几千条记忆」，MCP 解决「接入无限外部能力」。对"帮你完成所有事情"的贡献量级不在一个维度 |

### 层级四：交互体验（从「打字聊天」到「自然交互」）

#### 2.4.1 语音交互几乎为零

| 项 | 详情 |
|---|------|
| 现状 | Bridge 能接收社交平台语音消息，但没有 TTS / STT 引擎，没有语音唤醒 |
| 缺失 | 无法「说句话」唤出 Agent、无法语音对话、无法在开车/做饭时不看屏幕交互 |
| 为什么重要 | 打字是低带宽的交互方式。真正的助理应该你说话就能响应 |

#### 2.4.2 系统级快速唤起

| 项 | 详情 |
|---|------|
| 缺失 | 没有全局快捷键唤起、没有 Spotlight / Alfred 式快唤、每次都要切到 Hanako 窗口 |
| 为什么重要 | 每次交互的启动成本，决定了你「愿不愿意用」。超过 2 秒的唤起延迟会让用户宁愿自己动手 |

#### 2.4.3 通知智能分级

| 项 | 详情 |
|---|------|
| 现状 | `notify` 工具只是发通知，没有优先级概念 |
| 缺失 | "这个重要，立即打断我" / "这个不急，等我空闲时汇总一起说" / "这只是一条 FYI，不打扰" |
| 为什么重要 | 通知过少 = 错过重要信息；通知过多 = 关掉通知 = Bullshit As A Service |

#### 2.4.4 多模态理解弱

| 项 | 详情 |
|---|------|
| 现状 | Vision Bridge 能转述图片内容给纯文本模型 |
| 缺失 | 视频理解、屏幕实时理解、音频理解 |
| 为什么重要 | 世界不是纯文本的。会议是语音+画面，网页是视觉布局，图表是图形——Agent 需要理解这些 |

### 层级五：代码质量与技术债

这些问题不直接面向用户，但会随项目规模增长而放大维护成本和安全风险。

#### 2.5.1 IPC 文件访问无限制

| 项 | 详情 |
|---|------|
| 现状 | `read-file` / `read-file-base64` / `write-file` / `write-file-binary` / `open-file` 等 IPC 通道可读写任意绝对路径文件 |
| 位置 | `desktop/main.cjs:2909` / `3061` / `2924` / `2942` / `2890` |
| 风险评估 | `contextIsolation: true` + `nodeIntegration: false` 已启用，但若渲染进程存在 XSS 漏洞，攻击者可利用这些通道进行任意文件读写 |
| 建议 | 添加路径白名单校验（仅允许工作目录和 `HANA_HOME` 下的文件操作） |

#### 2.5.2 流资源泄漏风险

| 项 | 详情 |
|---|------|
| 现状 | `plugins/image-gen/routes/media.js:125-130`（`streamPipe` 客户端断连时未 destroy Node.js Readable）、`server/http/file-content.js:69-70`（`createReadStream` 转 Web ReadableStream 无错误处理）、`server/routes/resources.js:136-137` 存在类似问题 |
| 影响 | 长时间运行后可能累积未关闭的流句柄，导致内存泄漏或文件描述符耗尽 |
| 修复建议 | 在 `streamPipe` 的 `abort` / `error` 事件中主动调用 `readable.destroy()`；为 `createReadStream` 添加 `on('error')` 处理器并关闭底层流；考虑使用 `pipeline()` 替代手动 pipe |

#### 2.5.3 Session 文件操作缺乏事务性

| 项 | 详情 |
|---|------|
| 现状 | 归档/写入操作涉及主文件 + sidecar 两次独立 write，中间无事务包裹（`server/routes/sessions.js:856-903`） |
| 影响 | 进程崩溃时主文件和 sidecar 可能不一致，导致会话数据损坏 |
| 修复建议 | 引入写前日志（WAL）模式：先写入 `.tmp` 文件 → 原子重命名 sidecar → 原子重命名主文件；或改用 SQLite 事务包裹多文件操作 |

#### 2.5.4 品牌重命名残留

| 项 | 详情 |
|---|------|
| 现状 | Hanako → Jarvis 的品牌重命名已完成（`c3a77982`），但代码中仍有大量 `hana` 前缀的变量名、函数名、路径、环境变量（如 `HANA_HOME`、`hana-runtime-paths`、`hanaFetch`） |
| 影响 | 新贡献者困惑，品牌一致性受损，长期维护成本增加 |
| 建议 | 制定渐进式重命名路线图，优先用户可见的字符串和路径，内部变量可逐步迁移 |

## 三、优先级矩阵

```
                    低投入 ──────────────────── 高投入
```

## 四、一句话总结

你们现在的项目**已经有了一辆车的底盘、发动机、方向盘和四个轮子**。问题不在于缺某个零件，而在于：

1. **可靠性** → 车有时候会熄火（P0 问题：记忆、备份、电脑控制、代码签名、空 catch、无日志、非原子写入）
2. **缺少自动驾驶系统** → 只能手动挡，你得一步一步告诉它做什么（主动性鸿沟）
3. **缺少服务区地图** → 能去的加油站有限（生态集成不足）
4. **缺少语音助手和中控屏** → 交互方式单一，上车还得翻手册（体验问题）
5. **车身有旧标签** → 内部代码仍有大量旧品牌残留，维护成本随规模增长（技术债）

从「能用的工具」到「真正的 Jarvis」，核心突破点不是继续加工具数量，而是**从被动响应跨越到主动服务**——这需要架构层面的演进，不是加几个插件能解决的。
